# ux-tools

A collection of small, standalone tools for a UX designer. Each tool is a **single HTML file** that runs in the browser, **offline**, with no backend, storing data locally (localStorage / IndexedDB).

---

## 1. App build rules (hard requirements)

Every app in `apps/` **must** meet:

### 1.1 One file, zero external dependencies
- The whole app is a single `index.html` file (HTML + CSS + JS in one).
- **No build step**, no `node_modules`, no bundler. Opening the file in a browser = it works.
- **Vanilla JS only** — no frameworks (React/Vue/jQuery) and no runtime libraries.
- Allowed APIs: only what is built into the browser (Canvas, IndexedDB, Clipboard, File API, drag & drop, Web Storage).
- **No external assets**: system fonts, icons as inline SVG, no network requests. The app must work offline and without an internet connection.

### 1.2 Data persistence
- **Metadata / small state** → `localStorage` as a single JSON object under a versioned key, e.g. `ux-<tool>_v1`. The version in the key enables migrations.
- **Large blobs** (images, files) → `IndexedDB`. Never store large dataURLs in `localStorage` (~5 MB limit).
- A single `state` object as the source of truth; `save()` / `load()` functions wrapped in `try/catch` (localStorage can throw on overflow or in private mode).
- Migrations: on `load()`, handle migration from old/legacy keys, then clean up the old data.
- Every state change calls `save()`; app start calls `await load()` before the first render.
- Defensive `ensureActiveIndicesValid()` after every delete operation, so an active index never goes out of range.

### 1.3 Code architecture (conventions from image-slicer)
- One `state` object at the top of the script.
- Accessor helpers: `current*()` (e.g. `currentProject()`, `currentImage()`).
- CRUD operations as functions: `create*`, `add*`, `switch*`, `rename*`, `remove*`, `move*` — each calls `save()` + `render()`.
- Rendering split into independent `render*()` functions (`renderProjectList`, `renderEditor`, ...), coordinated by a single `render()`.
- Build the DOM imperatively (`document.createElement` + `appendChild`) and attach event handlers, rather than `innerHTML` from strings (security + performance for interactions).
- IDs generated by a `nextId` counter in state (stable identifiers for drag & drop and persistence).

### 1.4 No secrets / no backend
- The app never sends data anywhere. Everything stays on the user's device. Zero API keys, zero external endpoints.

## 2. Visual layer (design system)

All apps share **one consistent design system** (light by default + dark) derived from `image-slicer`, so the toolset reads as a single product. Colors are implemented **exclusively through CSS tokens** (custom properties) — never through hardcoded values in components.

### 2.1 Tokens and themes (light by default + dark)

Tokens are defined on `:root` (light) and overridden in `[data-theme="dark"]`. The active theme is set via the `data-theme` attribute on `<html>` (resolved `'light'` / `'dark'`); the choice is persisted in `state.theme` (`'light'` | `'dark'` | `'auto'` — `auto` follows `prefers-color-scheme` and updates live). **The default app theme is `light`.**

| Token | Light | Dark | Role |
|------|-------|------|------|
| `--bg` | `#f6f8fa` | `#111` | app background (`body`) |
| `--panel` | `#ffffff` | `#141414` | sidebar/section background |
| `--panel-2` | `#f1f3f5` | `#161616` | panel-header, row labels |
| `--panel-3` | `#eaecef` | `#1a1a1a` | app header, stages |
| `--inset` | `#ffffff` | `#1a1a1a` | input background |
| `--border` | `#d0d7de` | `#2a2a2a` | borders |
| `--border-soft` | `#e5e7eb` | `#1e1e1e` | cell separators |
| `--text` | `#1f2328` | `#e0e0e0` | primary text |
| `--text-2` | `#4b5563` | `#b9bfc6` | secondary text |
| `--text-3` | `#5c6670` | `#9aa0a6` | list content |
| `--text-4` | `#626a73` | `#8a9098` | section labels, empty states |
| `--accent` / `--accent-hover` | `#2563eb` / `#1d4ed8` | `#3b82f6` / `#2563eb` | primary, active elements, focus |
| `--danger` | `#d1242f` | `#f43f5e` | destructive actions |
| `--chip` / `--chip-text` | `#eaecef` / `#57606a` | `#2a2a2a` / `#888` | counters, badges |

| `--scrollbar` | `#c8d0d8` | `#2a2a2a` | scrollbar thumb |

In components use **only `var(--token)`**. Contrast of interactive elements ≥ WCAG AA in both themes. Visible `:focus-visible` ring (`outline: 2px solid var(--accent)`). Theme toggle in the header (`☀`/`☾`/`◐`), cycle `light → dark → auto`.

### 2.2 Typography
- Font: `-apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif` (system font — zero loading).
- Header `h1`: `15px / 600`.
- Section labels / panel-header: `10–11px`, `700`, `uppercase`, `letter-spacing 0.08–0.1em`, color `var(--text-4)`.
- List content: `12px`. Buttons: `12–13px / 500`.

### 2.3 UI components (keep consistent)
- **Buttons**: `.btn`, variants `.btn-primary` (filled accent), `.btn-ghost` (transparent + border), size `.btn-sm`. Action icons (✎ × ⠿ + ☀) are real `<button>` elements with `aria-label`.
- **Sidebar** (`<aside aria-label="…">`) with lists: drag-to-reorder, hover-reveal actions, inline rename, thumbnails.
- **Panel**: `.panel-header` (label + `.count` counter) + `.panel-body` (scrollable).
- **Drop zone / empty state**: dashed border `2px`, SVG icon, description, accent on hover/drag-over.
- **Custom scrollbars**: thin (`4–6px`), thumb `var(--scrollbar)`.
- **Resize handle** for a panel (e.g. sidebar) with the width persisted in state (`role="separator"`).

## 3. Interaction patterns (UX) — present in every app by default

- **Drag & drop** files into the window (upload) + reorder items in lists (with a `drag-over-above`/`below` indicator).
- **Paste from clipboard** (Ctrl+V) — wherever it makes sense (images, text).
- **Inline rename**: double-click on a name OR the ✎ icon; commit on Enter/blur, cancel on Escape.
- **Hover-reveal actions**: edit/delete icons visible only on hover of an item (less visual noise).
- **Live preview / immediate reaction** to changes (e.g. canvas re-rendered while dragging).
- **Export**: Download (anchor + `download`) and Copy to clipboard (`navigator.clipboard`) with feedback (button → "✓ Copied" for ~1.5 s, "✗ Failed" on error).
- **Keyboard**: Enter = commit, Escape = cancel in fields; focus management during inline editing.
- **Empty states**: every panel has a "no data" state with instructions on what to do.
- **Defensiveness**: `try/catch` around storage, filename sanitization (`safeFilename`), clamping of indices and values.

## 4. Repository structure

```
ux-tools/
├── CLAUDE.md                      # this document — conventions and requirements
├── apps/
│   └── <tool-name>/
│       ├── index.html             # the whole app (single-file)
│       └── README.md              # (optional) what it does, screenshot
└── .github/
    └── workflows/deploy.yml       # deploy apps/ to GitHub Pages
```

- Each tool has its own folder `apps/<name>/index.html` — this keeps the Pages URL clean (`.../ux-tools/apps/<name>/`) and leaves room for a README/assets, while `index.html` is served by default. The app itself stays single-file.
- Folder names: `kebab-case`, short and descriptive (e.g. `color-picker`, `aspect-ratio`, `contrast-checker`).

---

## 5. Creating a new app — checklist

1. Create the folder `apps/<name>/index.html`.
2. Copy the boilerplate: `<!DOCTYPE html>`, head with viewport, `<style>` with the design system (palette from section 2), structure of header + main + sidebar + panels.
3. Define `state`, `save()`, `load()` (with the versioned key `ux-<tool>_v1`) and the boot IIFE.
4. Build the CRUD (`create/add/switch/rename/remove`) + `render()`.
5. Add the patterns from section 3 as appropriate for the tool (drag & drop, paste, export, empty states).
6. Test: refresh → state is restored; delete data → empty state; overflow → IndexedDB instead of localStorage for blobs.
7. Add an entry to `apps/README.md`.

## 6. Hosting / deploy

Apps are published statically via GitHub Pages (workflow `.github/workflows/deploy.yml` uploading the `apps/` directory), identically to `image-slicer`. Each app is available at:
`https://<user>.github.io/ux-tools/apps/<name>/`

## 7. Naming conventions

- App folders, storage keys, IDs in HTML: `kebab-case`.
- JS functions: `camelCase`, prefixes `render*` / `add*` / `remove*` / `switch*` / `rename*` / `move*` / `ensure*`.
- State variables: `camelCase` (`activeProject`, `sidebarWidth`, `nextImageId`).
- DOM elements: `id` in `kebab-case`, references in JS as `camelCase` (e.g. `#btn-upload` → `btnUpload`).

## 8. Process and skills

Tools are built through a set of 5 skills in `.claude/skills/` (invoked as `/ux-<name>`). An adaptation of your `proto` repo to the scale of a single-file tool — lighter (one SPEC.md, one implementing skill, no ADRs and no multi-skill routing).

**New tool (from a spark):**
```
ux-idea   → apps/<name>/SPEC.md (Idea + Glossary sections)   [docs, no code]
ux-spec   → SPEC.md (Requirements section)                   [docs, no code]
ux-build  → apps/<name>/index.html                           [the ONLY skill that writes code]
```

**A live tool (feature / bug):**
```
ux-feature → "Change — feature" entry in SPEC.md (MVP plan, impact scope) → route to ux-build
ux-bug     → "Change — bug" entry in SPEC.md (repro, root cause file:line, fix plan, regression) → route to ux-build
ux-build   → implements the latest pending Change in index.html
```

Each skill: a one-question-at-a-time interview, English code names, a **git checkpoint** (commit before + after = a reversible stage). Full instructions in each `SKILL.md`.

**Indicating the tool:** `ux-spec`/`ux-build`/`ux-bug`/`ux-feature` work on an existing tool — you pass it as an argument (`/ux-build customer-journey`) or in a sentence; with a single existing tool the skill picks it on its own, with several it asks. `ux-idea` creates a new one, so the name is established during the interview (you can suggest it in the argument). The document capacity per app is **one `apps/<name>/SPEC.md`** with sections: Idea, Requirements, Glossary, Changes.
